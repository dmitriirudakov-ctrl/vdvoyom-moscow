# Подключение и публикация: по шагам

Сейчас готов локальный прототип. Для доступа с двух телефонов нужны аккаунты сервисов, база и адрес в интернете. Внешние аккаунты ещё не созданы.

## 1. GitHub

Зарегистрируйтесь на [github.com/signup](https://github.com/signup) и подтвердите email. Выбирайте бесплатный аккаунт. Пароль и коды подтверждения вводите сами на сайте; не отправляйте их в чат.

После регистрации сообщите только, что аккаунт готов. Следующие действия можно выполнить вместе с помощником: создать пустой публичный репозиторий `vdvoyom-moscow` и загрузить подготовленный код. Личные записи, экспорт данных, `.env.local` и исходные личные заметки в репозиторий не загружаются.

## 2. Supabase

После GitHub зарегистрируйтесь на [supabase.com](https://supabase.com/), например через вход GitHub. Условия сервиса принимает сам владелец. Создайте один проект на тарифе Free и сохраните пароль базы в менеджере паролей.

Проверьте доступность панели из вашей сети. Регион размещения выбирается при создании проекта; доступность самого приложения нужно отдельно проверить на обоих телефонах.

В SQL Editor выполните целиком файл `supabase/migrations/202610300001_initial.sql` один раз в новом проекте. Затем в Authentication отключите самостоятельную регистрацию пользователей.

## 3. Два аккаунта приложения

Аккаунты приложения отличаются от аккаунтов GitHub и Supabase.

- Выберите два разных логина из латинских букв и цифр, например `first` и `second`.
- В Supabase Authentication создайте двух пользователей со служебными email `first@weekend.invalid` и `second@weekend.invalid`. Пометьте email подтверждённым при административном создании; рассылка писем на эти адреса не используется.
- Задайте разные надёжные пароли. Вводите их сами; не публикуйте в Git и не отправляйте в чат.
- Создайте одну строку в `couples`. Запишите её ID.
- Создайте по строке в `profiles`: `id` — ID созданного пользователя Authentication, `couple_id` — общий ID пары, `display_name` — выбранное имя для интерфейса.

Для каждого шага таблицы открываются через Table Editor. При затруднении помощник может подготовить конкретный SQL с идентификаторами; пароли для этого не нужны. Клиент приложения сам не может создавать/менять членство в паре.

## 4. Публичные настройки

В настройках проекта Supabase найдите URL проекта и Publishable API key. Это клиентские настройки. Приватные `service_role`, `sb_secret_*` и пароль базы в код приложения не добавляются.

В локальном `.env.local` укажите:

```dotenv
VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_KEY
VITE_AUTH_EMAIL_DOMAIN=weekend.invalid
```

Перезапустите локальный запускатель. Вместо деморежима должен появиться экран входа. Войдите сначала в одном браузере, затем во втором из отдельного профиля и проверьте разделение записей.

## 5. Живая афиша

После работоспособного входа разместите функцию `import-events` через Supabase CLI. Административные команды выполняются владельцем или помощником в настроенной среде. Подготовленная команда:

```sh
supabase functions deploy import-events
```

Сгенерируйте отдельный случайный серверный `IMPORT_SECRET`, добавьте его в Secrets функции и в Supabase Vault под именем `weekend_import_secret`. В Vault также добавьте `weekend_project_url`. Секреты вводятся через панели или безопасный ввод, не через опубликованные команды с подставленными значениями.

Проверьте первый живой запуск. Только после успешного ответа и проверки записей каталога применяйте `supabase/cron.sql`. Повторное применение расписания с тем же именем обновляет его. Следите за статусом в `import_runs`.

Если источник отвечает 403, сохраняется работа с постоянными местами. Публиковать обещание работающей афиши в таком состоянии нельзя.

## 6. GitHub Pages

В репозитории откройте Settings → Secrets and variables → Actions → Variables и добавьте три публичные настройки из шага 4. Административные ключи здесь также не нужны.

В Settings → Pages выберите источник **GitHub Actions**. В Actions запустите workflow **Publish to GitHub Pages**. Он сначала выполнит проверки и сборку, затем разместит приложение и выдаст адрес. До первого успешного запуска опубликованного адреса нет.

## 7. Проверка на телефонах

Откройте полученную ссылку на обоих iPhone в Safari. Каждый входит под своим логином.

1. Создайте личное сохранение в первом аккаунте. Во втором оно не должно появиться.
2. Нажмите «Поделиться с партнёром». Теперь выбранное сохранение должно появиться у обоих; при необходимости обновите страницу. Открытый интерфейс также периодически обновляет общие данные.
3. Нажмите «Мы сходили» и проверьте общую историю.
4. Поставьте лайк месту и проверьте, что он виден в обоих аккаунтах.
5. Проверьте маршруты, экспорт, выход и повторный вход.
6. В Safari нажмите «Поделиться» → «На экран “Домой”».

Автоматическую Яндекс Погоду подключаем только после подтверждения применимости условий персонального API. Для запуска остальных функций она не обязательна.
